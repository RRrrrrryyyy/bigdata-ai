3个人解释

想象一位新入职的天才员工：智商极高、学习能力极强，但对你们公司的规矩一无所知——不知道周报用什么格式、PPT 要套什么模板、报销走什么流程。传统解法是每次干活前口头叮嘱一遍（这就像每次对话都粘贴一大段 prompt）；而 Skill 的做法是给这位天才发一本《新员工入职手册》：把"这类事在我们这儿怎么做"写成一册册文档，放在书架上。

关键在于手册不是一直摊在桌上的：每本手册的封面（技能名称和简介）始终可见，但正文只在任务匹配时才被翻开。这位天才看到"帮我做季度汇报 PPT"，才去抽出《品牌 PPT 规范》这本手册照着做；做代码审查时才翻《代码评审清单》。一本手册写一次、全团队复用，既沉淀了组织经验，又不占用桌面空间（也就是不浪费模型的上下文窗口）。

如果只能记住一句话：Skill 是打包了"某个领域该怎么做"的文件夹（以 SKILL.md 为核心），让通用 AI 助手在需要时自动加载，从通才变成专才——工具决定 AI"能做什么"，Skill 决定"怎么做"。

4核心机制

起源

2025 年 10 月，Anthropic 发布 Agent Skills；同年 12 月 18 日将其发布为跨平台可移植的开放标准。它回答的是 Agent 落地的核心缺口：通用 Agent 有智能、有工具，但没有领域专长——就像会解所有数学题的天才，未必比做过上千份报税单的老会计报得好税。Anthropic 的博客直言：他们因此"停止构建一个个专用 Agent，转而构建 Skill"。

原理：一个文件夹 + 三级渐进式披露

每个 Skill 是一个文件夹，核心是 SKILL.md 文件：YAML 元数据（name + description）声明"我是谁、何时用我"，正文是操作指南，可另附脚本（scripts/）、参考文档（references/）、模板资产（assets/）。它按需分三级加载：

  1. 第 1 级 · 元数据（常驻）：仅 name 与 description 进入系统提示，约 50-100 token。因此装几百个 Skill 也不撑爆上下文。
  2. 第 2 级 · 指令（触发时加载）：用户请求与 description 匹配时，模型才读取 SKILL.md 正文（应控制在 5k token 内）。
  3. 第 3 级 · 资源（按需加载）：脚本通过执行而非读入来使用（只有运行结果进入上下文），参考文档只在被引用时读取。

关键术语

SKILL.md：每个 Skill 的必备核心文件，YAML 前言 + Markdown 指令正文。
Frontmatter（元数据前言）：description 是触发匹配的依据，必须同时写清"做什么"和"何时用"。
渐进式披露（Progressive Disclosure）：元数据常驻、正文按需、资源更需的三级加载机制，是 Skill 不浪费上下文的关键设计。
触发（Trigger）：模型将用户请求与各 Skill 的 description 匹配、自动决定加载哪个 Skill 的过程；也可用 /skill-name 手动调用。
skill-creator：官方提供的"用 Skill 造 Skill"的元技能，引导用户交互式生成完整的 Skill 目录。

5应用场景

办公文档生成（日常办公）：Anthropic 预置了 PowerPoint、Excel、Word、PDF 等文档技能，内含专业排版与最佳实践，用户说"做个含公式的报表"即自动触发对应 Skill。
组织流程标准化（企业协作）：把公司的周报格式、品牌规范、发布流程写成 Skill，上传一次、全员复用——Claude Academy 的示例中，所有 PM 产出的状态报告自动遵循同一结构与语气，无需任何人复制粘贴模板。
沉淀重复性工作流（个人效率）：Claude Code 官方建议——"当你反复把同一段指令/清单/多步流程粘贴进对话时，就该做成 Skill 了"。例如 git 变更总结、代码评审清单、项目启动配方（recipe）的自动记录与复用。
合作伙伴生态（SaaS 集成）：Notion、Browserbase 等公司以 Partner Skill 的形式把自己的服务能力打包给 Agent 使用，形成"基础技能 + 伙伴技能 + 自建技能"的生态。
不适用场景：一次性简单指令与外部数据连接。只需一句话说清的事，直接写 prompt 即可，做成 Skill 反而增加维护负担；需要让 AI"连接和操作外部系统"（查数据库、发邮件）时，那是工具/MCP 的职责，Skill 解决的是"怎么做"而非"能做什么"。

6边界辨析

维度Skill（技能）Tool / MCP（工具）Prompt / System Prompt（提示词）
定义打包"某类任务该怎么做"的指令文件夹，按需自动加载连接数据与动作的接口（查代码、发邮件），由外部程序执行写在对话里的即时指令，随对话结束而消失
回答的问题"怎么做"（How）——流程、规范、最佳实践"能做什么"（What）——能力与数据通道"这次做什么"——单次任务的要求
复用性创建一次，跨对话/跨产品自动复用一次集成，随处调用每次对话都要重新粘贴
加载方式三级渐进式披露，触发才加载正文定义进工具列表，随调用执行始终占据当前上下文
一句话区分Skill 是入职手册，教方法Tool 是工具箱，给能力Prompt 是口头交代，说完即止

另可对比微调（Fine-tuning）：微调把知识"焊进"模型权重，成本高、更新慢；Skill 把知识放在文件系统里，用 Git 版本管理、随时可改，还能捆绑可执行脚本完成"生成 token 不可靠"的确定性操作——"代码即接口"正是 Skill 范式的核心理念。

7自测问题

1.（判断）Skill 是一种轻量级的模型微调。
参考答案错误。Skill 不改变模型权重，只是按需加载的指令文件；微调把知识"焊进"权重，成本高、更新慢。
2.（填空）SKILL.md 的元数据中，决定"何时触发本技能"的字段是 ____。
参考答案description。模型把用户请求与各技能的 description 匹配来决定加载哪个 Skill，因此它必须同时写清"做什么"和"何时用"。
3.（简答）三级渐进式披露中，哪一级常驻上下文？大约占用多少 token？
参考答案第 1 级（元数据），仅 name 与 description 进入系统提示，约 50-100 token——所以装几百个 Skill 也不会挤占窗口。
4.（选择）你发现自己每次对话都要粘贴同一段"周报格式要求"。按照官方建议，正确的做法是：A. 换更大的模型　B. 把它做成 Skill　C. 每次手动粘贴　D. 微调模型
参考答案B。Claude Code 官方文档："当你反复把同一段指令/清单/多步流程粘贴进对话时，就该做成 Skill 了。"
5.（辨析）Skill 回答"怎么做"（How），那么 Tool/MCP 回答的是____？
参考答案"能做什么"（What）——Tool 提供能力与数据通道，Skill 提供使用这些能力的流程、规范与最佳实践，两者互补。
