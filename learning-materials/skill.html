  • 能解释"渐进式披露"三级加载机制如何让 Skill 既强大又不撑爆上下文（对应第 4 节）。
  • 能区分 Skill 与提示词、工具/MCP、微调，并说出各自适用场景（对应第 6 节）。

2. 核心问题

  1. 提示词也能教模型做事，为什么还需要把知识打包成"Skill"这种文件结构？
  2. 装了几百个 Skill 的智能体，为什么上下文窗口不会被 Skill 的内容塞满？
  3. Skill 为什么强调"可以包含可执行脚本"，而不是全部用自然语言写说明？

3. 个人解释

想象你公司来了一位极其聪明但完全不懂行的新人。他学习能力强、什么都能干，但不知道你们公司的报销流程、不懂你们的设计规范、没听过你们的内部工具。你有两个选择：每次派活都站在他旁边口述一遍要求（这就是"提示词"）；或者，给他一套入职培训手册——每个主题一本小册子，封面写着书名和一句话简介，他遇到对应任务时自己抽出来翻看，看完就知道该怎么办。

Skill 就是这套给智能体的"入职手册"。Anthropic 在 2025 年推出 Agent Skills 时用的正是这个比喻：Skill 是一个文件夹，里面装着说明书（SKILL.md）、参考材料和可执行脚本，把"怎么做某类事"的程序性知识打包好；通用智能体装上它，就立刻变成某个领域的专家。妙处在于"按需翻阅"：手册不摊开时只占书架上的一格（约 100 token 的元数据），只有任务相关时才被打开读进上下文。

如果只能记住一句话：Skill 就是把"怎么做某类事"的知识打包成一个含 SKILL.md 的文件夹，让通用智能体按需加载、即插即用地变成专家。

4. 核心机制

起源

2025 年 10 月 16 日 Anthropic 正式发布 Agent Skills，用于解决"通用智能体缺乏领域程序性知识"的问题；2025 年 12 月 18 日，Anthropic 将 Agent Skills 作为开放标准发布，实现跨平台可移植。其设计动机是：随着智能体能力增强，需要可组合、可扩展、可移植的方式来注入领域专长，而不是为每个场景定制一个碎片化的新智能体。

原理：渐进式披露（Progressive Disclosure）三级加载

  • 第一级：元数据（常驻）——SKILL.md 开头的 YAML frontmatter（name + description），启动时即载入系统提示，每个 Skill 仅约 100 token，让智能体"知道有这些技能、何时该用"。
  • 第二级：指令正文（触发时加载）——当任务与 description 匹配，智能体通过 bash 读取 SKILL.md 全文（通常 5k token 以内），工作流程、最佳实践此时才进入上下文。
  • 第三级：资源与代码（按需加载）——Skill 目录里可捆绑参考文档（REFERENCE.md 等）与可执行脚本（.py 等），只在被引用时才读取或运行；脚本执行不占用上下文，理论上容量无上限。

这一设计让"装几百个 Skill"与"上下文不被撑爆"可以兼得，也是 Skill 区别于"把说明全写进系统提示"的关键。

关键要素（必掌握术语）

  • SKILL.md：Skill 的核心文件，必须以含 name 和 description 的 YAML frontmatter 开头。
  • Progressive Disclosure（渐进式披露）：按"元数据→正文→资源"三级按需加载的核心设计原则。
  • Composable（可组合）：多个 Skill 可叠加，智能体自动识别并协调使用。
  • Portable（可移植）：同一格式跨产品使用（Claude 应用、Claude Code、API），一次构建多处运行。

5. 应用场景

文档处理（Anthropic 预构建技能）：官方提供的 pptx、xlsx、docx、pdf 技能让 Claude 能真正创建和编辑电子表格、演示文稿与可填写的 PDF 表单——例如 PDF 技能通过附带脚本实现表单填充，这是纯对话难以做到的。
团队工作流沉淀（Claude Code / 企业）：团队把代码审查规范、发布流程写成自定义 Skill，通过版本控制共享，智能体在相关任务中自动遵循——"创建一次，自动生效"，不用每次对话重复叮嘱。
品牌与合规（企业知识注入）：把品牌视觉规范、法务合规模板打包成 Skill，让智能体生成的文档、邮件自动符合组织标准，把组织知识从"老员工脑子里"变成可复用资产。
不适用场景：一次性的临时任务。提示词是对话级指令，说完就完；Skill 的价值在"跨对话复用"。如果某件事只做一次，写清楚一段提示词就够了，打包成 Skill 是过度工程。

6. 边界辨析

维度提示词（Prompt）工具 / MCPSkill
定义对话中的一次性文字指令模型可调用的外部函数/接口（如经 MCP 协议接入）含指令+资源+脚本的文件夹，按需加载的领域知识包
侧重点"这次怎么做""能做什么"（能力接口）"这类事怎么做"（程序性知识）
典型用法临时交代要求、调整输出风格查数据库、调 API、执行动作沉淀工作流、规范、最佳实践并跨对话复用
一句话区分口头交代一次给一双手给一本可反复翻阅的操作手册

7. 自测问题

（判断）1. 一个 Skill 的内容在智能体启动时会全部读入上下文窗口。

参考答案

错。启动时只加载 YAML 元数据（约 100 token）；SKILL.md 正文在任务匹配时才读入，捆绑的资源与脚本按需加载——这就是渐进式披露。

（选择）2. SKILL.md 的 YAML frontmatter 必须包含哪两个字段？A. name + version B. name + description C. description + author D. name + tags

参考答案

B。name 和 description 是必填元数据，它们是渐进式披露的第一级，决定智能体"何时该用这个技能"。

（选择）3. 团队希望"代码审查规范在所有对话中自动生效，不用每次重申"，最合适的做法是：A. 每次对话写长提示词 B. 打包成 Skill C. 微调模型 D. 换一个更大的模型

参考答案

B。Skill 的价值正是"创建一次、跨对话自动复用"；提示词无法跨对话，微调成本高且不适合频繁更新的流程性知识。

（简答）4. 用"入职手册"的比喻解释 Skill 及其渐进式披露。

参考答案

Skill 像给聪明新人的一套入职手册：书脊上的书名和简介（元数据）让他知道有这本手册，遇到对应任务才抽出来读正文（SKILL.md），需要细节时再翻附录（捆绑资源），平时不摊开不占桌面（上下文）。

（简答）5. Skill 为什么允许捆绑可执行脚本，而不是全部用自然语言写说明？

参考答案

某些操作（如排序、填表单）用传统代码执行远比模型逐 token 生成可靠且便宜；脚本通过 bash 运行，结果确定且不占用上下文，是对模型能力的工程补位。
